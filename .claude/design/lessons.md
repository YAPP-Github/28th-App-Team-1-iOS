# 디자인 시스템 — 사고 사례

같은 실수를 두 번 하지 않으려고 남긴다. **규칙만 적지 말고 무엇이 어떻게 틀어졌는지**를 남긴다 — 이유를 모르면 다음 사람이 같은 판단을 반복한다.

**append-only.** 항상 파일 끝에 붙인다(`.gitattributes` 가 `merge=union` 이라 동시에 추가해도 충돌하지 않는다). 기존 항목은 고치지 않고, 뒤집힌 결론은 새 항목으로 적고 옛 항목에 «→ N번으로 갱신» 한 줄만 단다.

형식: `## N. 한 줄 제목` / 무엇이 틀렸나 / 왜 / 규칙.

---

## 1. 원본색 에셋에 `foregroundStyle` 을 걸어도 아무 일도 안 난다 (2026-07-26)

**무엇** — `OnboardingAnalysisView` 가 `Image.Ic.success` 에 `.foregroundStyle(Color.HilitGreen.g500)` 을 걸고 있었는데, `IcSuccess.imageset` 에 `template-rendering-intent` 가 없어 원본색으로 렌더됐다. 코드만 보면 초록으로 칠해질 것 같은데 실제론 무효인 줄이 남아 있었다.

**왜** — 에셋이 template 인지 원본색인지는 카탈로그 설정에 있고 호출부에서 안 보인다. 리뷰로 잡히지 않는 종류의 어긋남이다.

**규칙** — 색은 **에셋에 구워서** 쓰고 틴트하지 않는다. 색 변형이 필요하면 변형별 에셋을 따로 둔다(Figma 도 `default`/`dark`/`disabled` 를 따로 그린다). 토큰 주석에 원본색/template 여부를 명시한다.

## 2. SVG 라고 크기 하나로 돌려쓰면 안 된다 (2026-07-26)

**무엇** — 아이콘이 SVG 니까 24px 한 벌로 16px 자리도 덮을 수 있다고 판단했다가, 실제 path 를 재보고 뒤집혔다. `plus` 는 24px 판이 «글리프 20 / 막대 4», 16px 판이 «글리프 12 / 막대 2» — 24px 을 16 프레임에 넣으면 막대가 **33% 두꺼워진다.**

**왜** — 벡터는 해상도 문제만 해결한다. 크기별 획 두께 보정(optical sizing)은 디자이너가 다시 그린 결과라 스케일로 재현되지 않는다.

**규칙** — Figma 에 크기별 판이 따로 있으면 **쓰는 크기마다 에셋을 받는다.** 다만 안 쓰는 크기를 미리 받지는 않는다(번들·토큰 부풀림). 토큰 이름에 크기를 넣되 **그 패밀리에 크기가 하나뿐이면 생략**한다(`Left.default` vs `Cancel.dark24`).

## 3. 문서는 «주제»가 아니라 «경로»를 따라 고쳐야 한다 (2026-07-26)

**무엇** — 색 토큰을 Tuist 생성 접근자로 바꾸면서 `design.md`·`color.md` 는 고쳤는데 `lat.md/architecture.md` 가 옛 `Color.load` seam 을 그대로 들고 있었다. 주제가 «색»인 문서만 찾았기 때문.

**왜** — 심볼·파일 경로는 주제와 무관한 문서에도 인용된다(아키텍처 노트, 다른 스킬, 작업 문서).

**규칙** — 심볼·경로 이름을 바꿨으면 **옛 이름으로 `grep -rn --include="*.md"` 해서 걸리는 문서를 전부** 고친다. 직접 다룬 문서만이 아니다. 주제로 찾으면 반드시 샌다.

## 4. Figma 원본이 서로 안 맞을 때는 구현하고 기록한다 (2026-07-26)

**무엇** — 버튼 6종을 옮기다 시안 자체의 불일치를 3건 발견했다: `bottom/filled-2/gray` 라벨은 `b800` 인데 같은 회색 배경인 `2color` 왼쪽 라벨은 `g700` · `modal/dubble-button` 세로 padding 만 15(나머지 modal 은 16) · `Medium/black` 이 `status=outlined` 인데 테두리 없음.

**왜** — 시안은 사람이 그린 것이라 변형이 많아지면 서로 어긋난다. 코드에서 임의로 «맞춰» 버리면 디자이너는 영영 모르고, 나중에 시안을 고쳤을 때 코드와 또 갈라진다.

**규칙** — 임의 통일하지 말고 **시안대로 구현 + 문서에 «디자이너 확인 대기» 각주**를 남긴다. 오타가 명백한 경우(15↔16)만 고치되 `@ds` 태그로 원값을 보존한다.

## 5. Figma variant 축을 그대로 enum 으로 옮기면 안 된다 (2026-07-26)

**무엇** — 버튼 Figma 축이 `status` 에 `2button-1disabled`(상태), `color` 에 `default/pressed/disabled`(상태) + `gray/2color`(색)로 섞여 있었다. 그대로 옮기면 존재하지 않는 조합이 표현 가능해지고 상태를 손으로 넘기게 된다.

**왜** — Figma 축은 «화면에 늘어놓기 좋은 분류»지 «타입 설계»가 아니다. 특히 상태(pressed/disabled/selected)는 SwiftUI 가 이미 갖고 있다.

**규칙** — 축을 직교로 다시 자른다. 상태는 `ButtonStyle`(`configuration`·`isEnabled`)에, 화면 전체에 걸리는 것(light/dark 판)은 Environment 에, 슬롯·레이아웃을 갖는 것(2버튼)은 View 에 둔다. 남은 것만 enum 파라미터.

## 6. 「허브」라고만 쓴 규칙은 스킬 문서에서 샌다 (2026-07-29)

**무엇** — `CLAUDE.md`·`design.md` 가 «허브 문서에 토큰 개수·컴포넌트 이름을 열거하지 않는다»고 못박았는데 `skills/figma-screen/SKILL.md` 가 "컴포넌트 9종" 을 들고 있었다. 그 사이 10종이 되어 값까지 틀렸다.

**왜** — 규칙이 지목한 대상이 «허브(`design.md`·`CLAUDE.md`)» 라서, 같은 역할을 하는 스킬 문서가 규칙 밖으로 빠졌다. 스킬도 상세 문서를 가리키는 진입점이라 성질이 같다.

**규칙** — 개수를 갱신하지 말고 **열거 자체를 없앤다**. 대상은 문서 종류가 아니라 역할이다 — 상세 문서를 가리키는 모든 진입점(`.claude/CLAUDE.md`·`.claude/design.md`·`.claude/skills/*/SKILL.md`)에 개수·이름을 적지 않는다. 3번(경로로 찾기)의 짝 — 그쪽은 «어디를 찾나», 이건 «무엇을 애초에 안 적나».

## 7. `Text` 에는 스타일 프로토콜을 두지 않는다 (2026-07-29)

**무엇** — 표시용 태그(`tag` 1941:7132)를 `ButtonStyle` 처럼 `Text` 에 걸리는 스타일로 만들지 검토했다. SwiftUI 에 `TextStyle` 프로토콜은 없고(`Font.TextStyle` 은 `.body`·`.title` 열거형인 딴 것), 직접 만드는 것도 하면 안 된다.

**왜** — `ButtonStyle` 이 성립하는 건 `Button` 이 **opt-in 타입**이라 환경 전파가 하위 `Button` 만 골라 맞기 때문이다. `Text` 는 라벨·본문·제목에 다 쓰이니 같은 전파가 서브트리의 모든 `Text` 를 때린다. 게다가 `Text` 엔 `isPressed` 같은 상태가 없어 `configuration` 으로 받을 것도 없다 — 스타일 프로토콜이 주는 게 호출 문법뿐이다.

**규칙** — 탭 되면 `Button` + `ButtonStyle`, 표시만 하면 **View + 파라미터**. 자기 타입(`TagLabel` 등)에 스타일 프로토콜을 붙이는 건 가능하지만 `associatedtype` 탓에 타입지움 + Environment 키가 딸려오니, **환경 전파가 실제로 필요할 때만** 만든다(레포의 유일한 사례 `.hilitSurface(_:)` — 남이 짠 서브트리 깊은 곳의 버튼까지 미쳐야 해서 값을 한다).

## 8. 에셋을 다시 받으면 이름이 아니라 바이트로 대조한다 (2026-07-29)

**무엇** — 아이콘 148개를 전량 재수출해 갈아끼울 때, 이름만 보고 옛 토큰을 새 이름에 이어붙이려 했다. md5 로 전수 대조해 보니 **`Play` 와 `Stop` 이 서로 바뀌어 있었다** — ‖(세로 막대 2개)를 옛 코드가 `Play` 로 부르고 있었고, 재수출은 그걸 `Pause` 로 고쳐 왔다. 이름만 기계 치환했으면 재생 버튼과 일시정지 버튼이 뒤바뀐 채 **컴파일은 통과**했다. 같이 드러난 것: `dark`→`white` 개명 40건은 바이트 동일(순수 개명), `Left`·`Timer` 24px 은 이름이 같은데 다시 그려진 것, `loadingSuccess…` 는 `Success` 패밀리로 이사한 것.

**왜** — 에셋 이름은 디자이너가 붙인 라벨이라 그림과 어긋날 수 있고, 코드가 옛 라벨을 그대로 물고 있으면 어긋남이 양쪽에 복제된다. 이름 대조는 이 종류의 오류를 **구조적으로** 못 잡는다 — 타입도 컴파일러도 «어느 그림인가»는 모른다.

**규칙** — 에셋을 갈아끼울 땐 옛/새 파일의 **해시로 대응표를 먼저 만든다**(`md5` → 옛이름→새이름). 표에서 ① 1:1 로 붙은 것 = 순수 개명 ② 짝 없는 옛 이름 = 다시 그려졌거나 빠짐 ③ 짝 없는 새 이름 = 추가 로 갈라 처리하고, **교차 대응(A→B, B→A)이 나오면 멈추고 그림을 직접 열어본다.** 옮긴 뒤엔 «에셋 수 = 토큰 수, 고아 0» 을 확인한다.

## 9. 색 변수는 이름이 아니라 값으로 팔레트에 붙인다 (2026-07-30)

**무엇** — `modal`(2302:6098) 제목이 `Gray scale/800` 변수를 쓰는데 값이 #262A30 이다. 팔레트의 `g800` 은 #31333B — 이름만 믿고 옮기면 눈에 보이게 밝아진다. 값으로 대조하니 `g900`(#27282F)과 Δ≤2 로 사실상 같은 색이었다. 같은 파일의 다른 색은 전부 `grayscale/gray-N` 명명(`gray-500` #6D7183 등)이고 팔레트와 정확히 맞는다 — 즉 `Gray scale/N` 은 팔레트 확정 전 레거시 컬렉션이고 번호가 현행 스케일과 안 맞는다.

**왜** — 8번(에셋)의 색 버전이다. 변수 «이름» 은 디자이너가 붙인 라벨이라 컬렉션이 갈릴 때 번호가 어긋나는데, 이름으로 매핑하면 컴파일도 통과하고 토큰도 «있는 것»을 쓴 것처럼 보여서 리뷰에서 안 걸린다.

**규칙** — `get_variable_defs` 가 준 **HEX 로** 팔레트를 검색해 가장 가까운 토큰을 고른다(이름은 참고만). Δ 가 근사 범위(≈2/255) 안이면 토큰으로 흡수하고 `@ds(color)` 태그에 원값+이름 충돌을 적는다. 팔레트 어느 색과도 멀면(`CountdownCard` 의 #D2D6DE) 토큰화하지 말고 파일 내부 private 상수로 보류한다. **레거시 `Gray scale/N` 이름을 현행 `gray-N` 번호로 읽지 않는다.**

## 10. 「어긋난다」고 적어둔 값은 두 번째 증거가 나오면 고친다 (2026-07-30)

**무엇** — `TagLabel` 타이포가 `.body8`(sb12)로 구현돼 있었고 문서(`component.md`)엔 **«타이포가 어긋난다»는 각주만** 달려 있었다. `title-box`(2094:7912)를 옮기면서 그 안의 `tag` 노드(2000:8288)가 Medium 14 = `body6` 임을 확인했다 — px4 family 는 두 노드에서 같은 값이다. 각주를 남긴 시점에 이미 «px4 는 m14» 라고 적혀 있었으니, 코드만 다른 값이었다.

**왜** — 4번(시안 불일치는 구현하고 기록한다)을 잘못 적용한 결과다. 4번은 **시안 두 곳이 서로 다를 때** 임의 통일을 막는 규칙인데, 이건 시안은 일관되고 **코드만 틀린** 경우였다. 각주가 붙으면 «판단 보류»로 보여서 아무도 안 고치고, 그 값을 쓰는 화면이 늘수록 고치는 비용만 커진다.

**규칙** — 각주를 달 땐 «시안끼리 어긋남(디자이너 확인 대기)» 과 «코드가 시안과 어긋남(고쳐야 함)» 을 구분해 쓴다. 후자는 독립된 노드에서 같은 값을 두 번째로 확인하는 순간 고치고, 값이 바뀌는 화면을 보고서에 열거한다(여기선 `AxisCommentCard`·`GuestEvaluationView` 의 12→14pt).

## 11. 시스템 컴포넌트로 갈아타면 «안 그려지는 자리»가 생긴다 (2026-07-31)

**무엇** — 내비바 시안 높이가 44(= 시스템 표준)로 닫혀서 커스텀 54pt 바를 걷어내고 `.toolbar` 로 갈아탔다. 호출부 시그니처를 그대로 유지해 Onboarding 7화면이 무수정 컴파일됐고 스택 안이라 잘 나왔다 — 그래서 **시스템 바는 `NavigationStack` 안에서만 그려진다**는 사실이 검증을 그냥 통과했다. cover/sheet 로 스택 없이 올라오는 화면에서는 바가 조용히 사라진다(컴파일·린트·프리뷰 전부 통과).

**왜** — 수제 바는 `safeAreaInset` 이라 어디 붙여도 그려지는데, 시스템 바는 **컨테이너가 그리는 물건**이라 컨테이너가 없으면 요청이 조용히 버려진다. 모디파이어 시그니처가 같으니 호출부만 보면 두 경로의 차이가 안 보이고, 스택 안 화면만 확인하면 결론이 «잘 된다» 로 굳는다.

**규칙** — 수제 → 시스템 컴포넌트 전환은 **부모 컨테이너 전제가 생기는 일**로 취급한다. ① 전환 전에 그 컴포넌트를 쓰는 화면을 전수 조사해 컨테이너 밖 사례를 찾는다 ② 밖에 있는 화면용 경로를 같이 만들고 이름에 조건을 박는다(`.hilitPresentedNavigationBar` — 이름이 «언제 쓰나»를 답한다) ③ 룩이 갈리지 않게 공유 지점을 남긴다(`HilitNavigationBarSlot`). 검증은 «컨테이너 안» 과 «컨테이너 밖» 을 둘 다 본다 — 한쪽만 보면 조용한 실패는 안 잡힌다.

## 12. 「시안에 없다」를 「불가능하다」로 적으면 시안 개정에 뒤집힌다 (2026-07-31)

**무엇** — 내비바 문서·독스트링에 «뒤로 버튼 없음 — leading X **고정**이라 슬롯이 아니라 `onClose` 액션» 이라고 적어 뒀는데, 0729 시안의 3행 매트릭스를 전수 대조하니 «왼쪽 아이콘 미노출» 칸이 두 곳(439:10396 icon 행 · 439:10399 text 행)에 실재했다. leading 은 상수가 아니라 끌 수 있는 슬롯이었고, `showsClose` 파라미터가 뒤늦게 붙었다.

**왜** — «지금 시안에 그 변형이 없다» 는 관찰이고 «leading 은 상수다» 는 설계 단언이다. 관찰을 단언으로 승격해 적으면 시안이 개정될 때 문서가 조용히 거짓이 되고, 다음 사람이 «불가능» 이라고 읽어 그 변형을 찾지 않는다. 매트릭스를 한 칸씩(«max» 케이스만) 보고 옮긴 것도 원인이다 — 없는 칸이 «없는 조합» 인지 «안 그린 칸» 인지 구분하지 못했다.

**규칙** — ① 시안에 없는 변형은 «지금 시안엔 없다 + 노드 근거» 로 적는다. «불가능·고정·상수» 는 타입이 실제로 막을 때만 쓴다. ② variant 매트릭스는 **행 × 열 전수 대조** 한다 — 빈 칸을 발견하면 «없는 조합인가, 다른 행과 같은 그림이라 안 그린 것인가» 를 판정해 근거로 남긴다(내비바 text 행의 «오른쪽 아이콘 미노출» 이 후자였다). ③ 슬롯을 끄는 건 «안 그리기» 가 아니라 **폭을 남기고 비우기** 다 — 시안이 빈 40×26 박스를 그려둔 이유가 그것이고, `.toolbar` 에서 `ToolbarItem` 을 아예 빼면 `.principal` 타이틀이 빈 쪽으로 끌려간다(`.principal` 은 바 전체가 아니라 leading/trailing 이 남긴 공간의 중앙을 잡는다).

## 13. 같은 Figma 노드를 소비하는 컴포넌트는 한꺼번에 훑는다 (2026-07-31)

**무엇** — 10번에서 `TagLabel` 의 12→14pt 오구현을 고치면서 «그 값을 쓰는 화면» 만 열거했는데, 같은 `tag`/`tag-with-icon` 노드를 소비하는 `SaveIndicator` 가 목록에 없었다. 라벨이 여전히 12pt 로 남아 같은 버그가 한 컴포넌트에 살아 있었고, 이번에 `body5`(sb14)로 다시 고쳤다.

**왜** — 10번의 수정 범위를 «`TagLabel` 을 쓰는 곳» 으로 잡았지만, 실제 오염 범위는 «그 Figma 노드의 값을 옮겨 적은 곳» 이었다. `SaveIndicator` 는 `TagLabel` 을 쓰지 않고 같은 시안을 **각자 구현**했기 때문에 심볼 검색에 안 걸린다 — 코드 의존이 없는 복제라 컴파일러도 침묵한다.

**규칙** — 시안 값을 고칠 땐 심볼(`TagLabel`)이 아니라 **Figma 노드 이름으로** 레포를 훑는다(`grep -rn "tag-with-icon"` — 독스트링에 노드 근거를 적어 두는 규칙이 여기서 값을 한다). 같은 노드를 소비하는 컴포넌트가 둘 이상이면 전부 고치고 보고서에 열거한다. 3번(주제 말고 경로로 찾기)의 시안 버전이다.

## 14. 컴포넌트 시트의 조각 크기는 컨테이너가 `flex-1` 이면 렌더 크기가 아니다 (2026-07-31)

**무엇** — `DashIndicator` 를 «20×4 조각을 나열하는 것» 으로 읽어 고정폭 조각을 늘어놓게 구현했다. 실제 시안(«progress bar» 435:1575)은 컨테이너가 px20/py4·gap2·h12 를 소유하고 조각은 `flex-1` 로 **등분**된다 — 375 폭 5단계에서 조각은 65.4 이고 20 은 컴포넌트를 그려둔 기본 폭일 뿐이었다. 결과로 이 컴포넌트는 어느 화면에서도 시안처럼 안 나와서 **아무도 쓰지 않았고**, 온보딩 6화면이 같은 진행 바를 값 하드코딩으로 각자 재발명했다.

**왜** — 컴포넌트 시트는 조각을 «대표 크기» 로 그려 둔다. 그 수치는 auto-layout 안에서 부모의 크기 정책(hug/fill/flex)에 덮이는데, 조각만 확대해 보면 부모 정책이 시야에 없다. 조각 w/h 가 «수치» 로 보이니 근거가 확실해 보이는 것도 함정이다.

**규칙** — 조각 크기를 믿기 전에 **컨테이너의 레이아웃 속성**(폭 정책·gap·패딩)을 먼저 읽는다. 조각이 `flex-1`/`fill` 이면 코드도 `frame(maxWidth: .infinity)` 로 옮기고, 시안 폭에서 계산이 떨어지는지 프리뷰로 확인한다(375 에서 65.4). 그리고 **«DS 에 있는데 아무도 안 쓰는 컴포넌트» 는 오독 신호다** — 화면들이 같은 것을 하드코딩으로 재발명하고 있는지 본다.

## 15. 에셋이 「없다」는 판단은 패밀리 이름이 아니라 svg 내용으로 한다 (2026-07-31)

**무엇** — 게스트 온보딩 가이드 행의 40×40 아이콘 타일(b800 판 + 초록 24 글리프)을 «DS 에 없다» 고 판단해 도형·색을 손으로 조립했다. 나중에 대조해 보니 `Img.person`·`Img.talk` 이 Figma 노드(`person/40px` 435:656 · `talk/40px` 435:652)와 **byte 동일**하게 이미 들어와 있었다.

**왜** — 그 두 에셋이 아이콘이 아니라 **일러스트 패밀리(`Img`)에 분류**돼 있었다. «40px 타일 아이콘» 을 찾으면서 아이콘 패밀리만 뒤졌고, 이름 검색(`person`)도 일러스트 목록을 훑지 않으면 눈에 안 들어온다. 8번(이름이 아니라 바이트)·2번(크기별 판)의 검색 버전 — 분류 축이 하나 다르면 이름 검색이 구조적으로 샌다.

**규칙** — «없다» 는 결론은 **에셋 카탈로그 전수** 를 훑고 내린다(`Assets.xcassets` 디렉터리 나열 + `Image+Extension.swift` 전체 — 패밀리 이름으로 좁히지 않는다). 손제작 직전에 «시안 노드의 svg 와 같은 그림이 이미 있나» 를 한 번 더 묻고, 확인했으면 판단 근거를 주석에 남긴다. 완성형 타일 에셋처럼 분류가 헷갈리는 것은 `design/image.md` 에 «감싸지 말 것» 을 적어 다음 사람이 같은 조립을 안 하게 한다.

## 16. Figma 컴포넌트가 다른 컴포넌트를 품고 있으면 그 자리는 슬롯이다 (2026-07-31)

**무엇** — `file-upload` 의 `progressing`·`completed` 행을 그 컴포넌트의 고유 레이아웃으로 읽고 안에 직접 그렸는데, 실은 별도 컴포넌트 «card»(card-pdf)의 **인스턴스**였다. 같은 일이 `home modal` 의 `port` 케이스에도 있었다 — 타이틀 아래 파일 카드가 역시 `card-pdf` 인스턴스다.

**왜** — `get_design_context` 가 뽑아 주는 레이아웃은 인스턴스를 펼쳐서 준다. 펼친 결과만 보면 «이 컴포넌트가 소유한 줄» 과 «남의 컴포넌트를 얹은 자리» 가 구분되지 않아, 같은 그림을 두 파일에 복제하게 된다(그 뒤엔 한쪽만 고치는 버그가 따라온다).

**규칙** — 시안을 옮길 때 **인스턴스 경계를 먼저 확인한다**(노드 이름에 컴포넌트명이 남아 있거나 metadata 에 instance 로 나온다). 남의 컴포넌트가 앉은 자리는 코드에서도 **슬롯**(`@ViewBuilder content:`)으로 열고, 그 컴포넌트가 아직 DS 에 없으면 슬롯 + «생기면 여기에 넣는다» 주석으로 둔다(`HomeModal.content`). 이미 복제해 그렸다면 독스트링에 «어느 컴포넌트의 인스턴스인지» 를 적어 합칠 지점을 남긴다(`FileUpload.fileRow`).

## 17. variant 이름과 글리프가 뒤집힌 컴포넌트가 있다 — 이름이 아니라 글리프로 맞춘다 (2026-07-31)

**무엇** — «video-control» 의 variant 이름과 내용이 서로 반대였다: `video-control/play`(435:830) 안에 `pause/34px` 글리프가, `video-control/pause`(435:837) 안에 `play/34px` 글리프가 들어 있다. 이름대로 옮기면 재생 중에 ▷ 가 보이는 버튼이 된다.

**왜** — 8번(에셋 `Play`/`Stop` 이 서로 바뀐 채 컴파일 통과)의 **컴포넌트 variant 이름** 버전이다. 디자이너는 variant 이름을 «지금 상태»(재생 중) 로 붙이고 글리프는 «누르면 할 일»(멈춤) 로 그리는데, 코드는 보통 반대 관례를 기대한다. 어느 쪽이든 이름만 보면 판별이 안 된다.

**규칙** — 상태 → 글리프 매핑은 **글리프를 열어 보고** 정한다. 정한 방향을 API 이름으로 못박고(`isPlaying: Bool` — «지금 상태» 임을 이름이 말한다) 독스트링에 «어느 노드에 어느 글리프» 를 적는다. `Play`/`Pause`·`Start`/`Stop` 처럼 뒤집혀도 컴파일되는 짝은 항상 이 절차를 밟는다.

## 18. 레거시 변수 컬렉션은 색만이 아니라 텍스트 스타일도 갈린다 (2026-07-31)

**무엇** — 9번은 레거시 `Gray scale/N` 색 변수의 번호가 현행 스케일과 안 맞는다는 것이었다. 텍스트 스타일에도 같은 일이 있다 — 레거시 `Head/head4_sb_24` 는 행간 1.3 인데 현행 `head/head4` 는 1.35 다. 레거시를 읽고 «코드의 1.35 가 틀렸다» 고 판단해 토큰을 고치면 현행 스타일 전체가 어긋난다.

**왜** — 9번의 텍스트 버전이다. 변수 컬렉션이 갈릴 때 이름은 남고 값만 바뀌는데, 색은 «눈에 보이게 밝아짐» 으로 티가 나는 반면 행간 0.05 차이는 리뷰에서 안 보인다. 게다가 타이포는 토큰이 전역이라 한 번 잘못 고치면 화면 전부가 미세하게 밀린다.

**규칙** — 시안에서 읽은 텍스트 스타일 값이 토큰과 다르면 **먼저 그 변수가 어느 컬렉션인지** 본다(레거시 `Head/head4_sb_24` 식 이름 vs 현행 `head/head4`). 레거시면 코드를 고치지 않고 «레거시 값 = N, 현행 토큰 = M» 을 기록만 한다. 현행 컬렉션끼리 어긋날 때만 4번(시안 불일치) 절차로 간다.

## 19. 「컨테이너가 여백을 소유한다」는 가정은 세그먼트가 각자 배경을 가지면 깨진다 (2026-07-31)

**무엇** — `ButtonLarge` 2버튼은 컨테이너가 좌우 24 여백을 소유하고 세그먼트는 라벨만 그리는 구조였다. `.twoColor`(왼쪽 회색 · 오른쪽 검정 반반)를 이 구조에 넣으니 각 반쪽의 **배경이 컨테이너 여백 안에서 끝나** 좌우에 24pt 씩 빈 띠가 생겼다. 시안은 반쪽이 정확히 187.5(=375/2) 로 화면을 꽉 채우는 full-bleed 다.

**왜** — 여백이 투명하면 «누가 여백을 갖는가» 가 화면에서 안 보인다. 공유 배경 톤(`dark`·`gray`)에서는 컨테이너 배경이 여백까지 칠해 주니 잘못된 소유 구조가 정답처럼 보였고, 세그먼트가 배경을 갖는 변형이 들어오는 순간에만 드러났다. 프리뷰를 흰 배경에 놓으면 24pt 갭이 흰색이라 더 침묵한다.

**규칙** — 배경을 가진 조각을 나열할 때 **여백 소유를 조각 쪽으로 내린다**(`.twoColor` 는 컨테이너 패딩 0 + 반쪽이 `contentInsets` 를 직접 갖는다). full-bleed 여부는 «시안 폭에서 조각 폭이 정확히 떨어지는가» 로 검증한다(375 → 187.5) — 프리뷰에 `.frame(width: 375)` 와 배경색을 주고 눈으로 확인한다. 여백 정책이 변형마다 다르면 값을 한 곳(`pairInsets(tone:)`)에 모아 «어느 변형이 왜 다른가» 를 그 자리에 적는다.
